# ScienceLogic–Remedy Ticket Integration

## Overview

The responsibility of this application is simple:

> **Whenever ScienceLogic generates an event, decide whether a ticket should be created or updated in Remedy, perform all validations and business rules, and then update ScienceLogic with the result.**

The application acts as a **workflow engine between ScienceLogic and Remedy**.

It does not generate alerts.

It does not monitor devices.

It only reacts to events generated by ScienceLogic.

---

# Architecture

At a high level, the integration involves three main systems:

```text
                ScienceLogic
                     │
                     │
          Event Trigger (Runbook)
                     │
                     ▼
             Python Integration
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
     ScienceLogic API        Remedy SOAP
          │                     │
          └──────────┬──────────┘
                     ▼
              Event Updated
```

The Python application acts as the **middleman between ScienceLogic and Remedy**.

Its responsibility is to:

1. Receive event information from ScienceLogic.
2. Validate the event.
3. Apply business rules.
4. Decide whether a ticket should be created or updated.
5. Communicate with Remedy.
6. Update the ScienceLogic event with the result.
7. Handle retries and failures.

# What Happens Before Python Starts?

One of the most important things to understand is that the Python application is **not the starting point of the workflow**.

A significant amount of processing has already happened before the Python script starts.

---

# Step 1: ScienceLogic Monitors Infrastructure

ScienceLogic continuously monitors infrastructure and applications.

Examples include:

* Servers
* Switches
* Routers
* SQL databases
* NetApp systems
* Network interfaces
* SSL certificates
* F5 devices
* QRadar
* Windows clusters
* Components
* Hundreds or thousands of devices

ScienceLogic continuously polls and evaluates these resources.

Example conditions:

```text
Switch is Down

CPU High

SQL Database Full

Certificate Expired

Interface Down
```

ScienceLogic detects these conditions.

At this stage, the Python application is not involved.

---

# Step 2: ScienceLogic Creates an Event

Suppose a switch becomes unavailable.

```text
Switch XYZ is Down
```

ScienceLogic creates an event.

Example:

```text
Event ID      : 145236
Severity      : Critical
Policy        : Device Down
Organisation  : ABC
Device        : Switch XYZ
Message       : Device unreachable
```

The event is stored inside ScienceLogic.

The Python application is still not involved.

---

# Step 3: Automation Policy Is Triggered

ScienceLogic contains Automation Policies.

An automation policy may be configured like this:

```text
IF

Event Policy = Device Down

THEN

Run Python Script
```

This is the point where the Python integration begins.

ScienceLogic launches the Python script through the configured runbook automation.

---

# Step 4: ScienceLogic Injects Event Information

The Python application does not initially query ScienceLogic to discover the event.

Instead, ScienceLogic passes the current event information directly to the script.

Examples include:

```text
Event ID
Device Name
Policy
Severity
Organisation
Device Class
Interface
Root Device
Message
User Note
External Ticket
```

These values are available through:

```text
EM7_VALUES
```

`EM7_VALUES` can be understood as:

> **The current ScienceLogic event context.**

It contains the event information required by the automation.

# Step 12: Business Rule Engine

The business rule engine is the core of the application.

The application now determines:

> **Should this ScienceLogic event become a Remedy ticket?**

Hundreds of business rules may be evaluated.

Example workflow:

```text
Availability Event?
        │
        ▼
Handle Availability Rules
```

```text
Interface Event?
        │
        ▼
Check AUTO TICKET Tag
        │
        ├── Tag Exists
        │       │
        │       ▼
        │   Continue
        │
        └── No Tag
                │
                ▼
        Do Not Create Ticket
```

```text
SQL Event?
        │
        ▼
Modify Ticket Payload
```

```text
NetApp Event?
        │
        ▼
Apply NetApp Rules
```

```text
SSL Event?
        │
        ▼
Append Certificate Details
```

```text
QRadar Event?
        │
        ▼
Check Magnitude
        │
        ├── Above Threshold
        │       │
        │       ▼
        │   Continue
        │
        └── Below Threshold
                │
                ▼
             Ignore
```

```text
Vesta Event?
        │
        ▼
Extract Vendor Case
```

Business rules may perform different actions.

A rule may:

* Modify the ticket payload.
* Reject ticket creation.
* Acknowledge the ScienceLogic event.
* Change the device name.
* Change the application type.
* Add additional information.
* Query the ScienceLogic database.
* Apply organisation-specific logic.
* Apply device-specific logic.
* Apply policy-specific logic.

At the end of the business rule engine, one of two results is produced:

```text
Valid Ticket Payload
```

or

```text
No Ticket Required
```

# Failure and Retry Workflow

The application contains a built-in retry mechanism.

Suppose Remedy is unavailable.

```text
Remedy Failure
      │
      ▼
Update ScienceLogic User Note
      │
      ▼
Mark Retry 1
      │
      ▼
Next Automation Execution
      │
      ▼
Retry Request
      │
      ▼
Retry 2
      │
      ▼
Retry 3
      │
      ▼
Retry 4
      │
      ▼
Retry 5
      │
      ▼
Still Failing?
      │
      ▼
Mark Final Failure
      │
      ▼
Generate ScienceLogic Alert
      │
      ▼
Stop
```

The application does not immediately give up when an external system fails.

Instead, it tracks retry attempts and allows subsequent executions to retry the operation.

After the maximum retry limit is reached:

* The failure is recorded.
* ScienceLogic is updated.
* A failure alert may be generated.
* Processing stops.

This provides a built-in recovery mechanism.

# Summary

> **This application is a workflow engine that sits between ScienceLogic and Remedy. It receives an event from ScienceLogic, enriches and validates the event using business rules and additional data, decides whether a ticket should be created or updated, communicates with Remedy, writes the outcome back to ScienceLogic, and handles retries and failures to ensure both systems remain synchronised.**

In simple terms:

```text
ScienceLogic detects the problem.

Python decides what to do.

Remedy manages the ticket.

Python updates ScienceLogic with the result.
```
